# Hop v2 会话协议（开发中，尚未接入产品）

本文是平台实现的共同字节约定，不代表配对、会话、剪贴板或跨设备输入已经完成或经过安全评审。现有 v1 仍是独立明文协议，不与此协议自动降级或复用 token。

## 身份与连接

- 每设备持有独立证书和私钥。首次交换证书时，双方分别显示本机及对端证书完整 SHA-256 指纹，用户通过可信的独立渠道核对两端对应指纹后才允许保存对端证书；网络发现、名称、地址、六位码和未核验的证书都不是可信身份。取消、超时或指纹不一致必须删除待确认状态，不能建立可信连接。私钥存系统安全存储，解绑删除对应信任；密钥与剪贴板内容不记日志。指纹交换和 UI、平台存储仍待实现和安全评审。
- 首次配对的证书获取与可信建立分开：一条短时、长度受限的候选交换连接仅传每端一个公开证书及临时标识，不传私钥、键鼠或剪贴板，并有超时及并发上限；该连接上的地址、名称、标识和证书一律只是候选。候选消息解析拒绝多证书、异常长度和重复帧。各端展示各自与候选对端的完整指纹，用户在独立可信渠道核对后才允许为这一次建立临时 pin；取消、超时和窗口关闭丢弃候选。随后在新的 TCP 连接上用该次精确证书进行双向 TLS 固定，收到并核验双方 PAIR_CONFIRM 后才持久化。候选编码如下，实际服务、速率限制及 UI 仍需实现和单独评审。
- 已配对重连时，如服务端需要预先选择一个已保存的对端 pin，可在 TLS 前读取长度受限的公开指纹作为本地查找提示；该提示本身不授予信任，必须在 TLS 后再次严格匹配对应证书，未知值拒绝或进入用户显式启动的首次配对，不能静默信任。实现亦可使用其他能完成相同精确固定的安全方式。
- 每次连接双向固定上述已确认的证书，TLS 1.3 双向认证成功前不发送或解析应用帧；失败即关闭，不回退明文。一个连接恰好有一个 host 和一个 receiver。手动更换主机需明确结束旧焦点及旧会话，不能静默夺取。
- 以下整数均为无符号大端（明确标为 i32 的为二补码有符号大端）。最大帧及顺序见 `core/include/hop/frame.h`。双方各自从 1 开始递增 sequence，每个连接独立计数；所有包头 reserved 均必须为零。控制、输入、剪贴板控制的 payload 最长 4096 字节，clipboard chunk 最长 65536 字节。TCP 是字节流，允许任意拆分和合并，不能假定一次读写完整一帧。
- 每个 payload 前 4 字节是 `schema=1:u8, opcode:u8, reserved:u16=0`。以下长度均包括这 4 字节；未识别 schema/opcode、错误长度、非法枚举和非零 reserved 均关闭会话，先恢复本地及释放已注入输入。初始阶段仅允许 HELLO/HELLO_ACK 及所需的配对确认；不允许屏幕、输入或剪贴板。

## 首次候选与重连查找编码

首次配对必须由用户显式启动且有短时有效期。候选连接每端只发一个 `HPOP` 帧并关闭，不升级同一连接为 TLS：4 字节 ASCII `HPOP`、`version:u8=1`、`role:u8`（host=1、receiver=2）、`name_length:u16`、`certificate_length:u32`、`nonce:16 bytes`，随后是设备名 UTF-8 字节和单个 PEM 证书字节。发起端发完后半关闭写侧；响应端读取至 EOF，确认恰好一个完整帧且无尾随字节后才回复自身 HPOP 并关闭。发起端读取回复至 EOF 并做相同边界检查。名称 1…128 字节，不含控制字符、双向文本覆盖及隔离控制符；证书 1…16384 字节，只允许一个有效证书；nonce 由安全随机源生成且不得全零。长度、UTF-8、证书和帧边界有任一错误，或收到额外数据，立即关闭。nonce 是本次候选标识，不是身份或认证凭据；证书摘要必须由接收端本地重新计算。双方显示两个完整指纹时名称只是未认证提示。

双方人工核对后，在新的 TCP 连接开始处由发起 TCP 连接的一端发送 68 字节：`HPSL` 加**发起端自身证书**的 64 个大写十六进制 SHA-256 字符；接收连接的一端只用它查找本地已保存的对应证书，或当前用户已核对的短期候选证书。接收端必须使用选出的证书完成双向 TLS 精确固定，未知值拒绝，不凭此前缀建立信任。这个前缀和 TLS 必须在一个有界、单连接的串行状态机中准确消费；TLS 字节不得被误吞。客户端在 TLS 后再次核对 peer fingerprint；超时、取消或断线清除候选。首次确认流程见 PAIR_CONFIRM；单侧先保存不构成另一侧已保存的证明。

## 会话与焦点代号

主机以密码学随机源选择 `session_epoch`（1 到 2^63−1），放在首帧 HELLO 的外层 epoch。接收端认证后接受此值，并用同一 epoch 回复 HELLO_ACK。SCREENS、HEARTBEAT、BYE 使用 session_epoch。之后主机依次分配大于 session_epoch、在该连接内严格递增的非零 `focus_epoch`；接近 u64 上限应结束连接，不回绕。每次 ENTER 使用新的 focus_epoch，ENTER_ACK、该次输入、剪贴板、REQUEST_LEAVE、RELEASE、RELEASE_ACK 使用同一 focus_epoch。新 TLS 会话重新选择 session_epoch 和 sequence。

只有 ENTER 经接收端明确 ACK 后，主机才能将输入转发到该目标。切换时先停止旧目标发送，发 RELEASE 并等待 RELEASE_ACK，再向新目标发 ENTER 并等待 ACK；任何超时、拒绝、断线、锁屏、权限撤销或队列满都先恢复本地，尽力释放远端所有已按键/鼠标键，不能静默吞键。协商了剪贴板时，接收端收到 RELEASE 必须立即撤销焦点并释放注入状态，异步等待本地剪贴板 actor 的撤销屏障完成后才发 RELEASE_ACK；主机也必须同时等自身 actor 撤销屏障和远端 ACK，才可进入下一个焦点。屏障最多等待 2 秒，超时断开；不等待时不得确认完成。未协商剪贴板时可立即 ACK。连接丢失时同样释放。旧焦点 epoch 的数据不得注入、覆盖当前剪贴板或破坏当前传输；非法状态和资源越界关闭连接。处理器必须串行化同一连接状态，不在物理输入回调中阻塞网络、磁盘或 UI。

双方至少每秒发送一次 HEARTBEAT；持续 3 秒未收到合法帧视为断线。系统休眠或实际调度延迟等需实机验证，不能将其当作可靠的实时保证。拥塞、磁盘、剪贴板编解码不应阻塞计时及释放流程；发送队列应有界，键盘／按钮不能静默丢弃，移动事件可合并；每个图片分块之间优先处理控制和输入。

## Control（frame kind 1）

- `0x01 HELLO`、`0x02 HELLO_ACK`：长度 16；前缀后为 `role:u8`（host=1、receiver=2）、`platform:u8`（macOS=1、Windows=2、Linux=3、HarmonyOS=4）、`reserved:u16=0`、`capabilities:u64`。主机先发 HELLO，接收端以 receiver 角色答 ACK。bit 0 为基础鼠标／键盘，bit 1 为文本剪贴板，bit 2 为 PNG，bit 3 为水平滚轮，bit 4 为前进／后退键；bit 5 表示此端需要首次配对确认，属于会话状态标志而非输入能力。未定义的位必须为零，未协商能力不得使用。真实系统能力和权限以对应平台检测为准。
- `0x04 PAIR_CONFIRM`、`0x05 PAIR_CANCEL`：长度 4，使用 session_epoch。双方先各自通过可信独立渠道核对完整的本机与对端指纹，再以临时证书固定建立双向 TLS。若任一端 HELLO 设置 bit 5，两端必须分别由用户确认，并在已认证 TLS 上各自发送 PAIR_CONFIRM；只有本端确认和收到对端确认后才能持久保存信任、接收 SCREENS 或开始控制。PAIR_CANCEL、超时、断线或不一致立即关闭并丢弃临时信任；如果一方已保存而另一方尚未保存，则下次仍由需要确认的一方设置 bit 5，双方再次确认，不能自动降级。已互信的常规重连均不设置该位。
- `0x03 SCREENS`：长度 `8+24*n`；前缀后 `count:u16`、`reserved:u16=0`，再按顺序列出 `screen_id:u64, x:i32, y:i32, width:u32, height:u32`。每设备最多 64 屏，ID 在此连接中非零且唯一，宽高范围 1…65535，x/y 与边界计算须防溢出。坐标为目标设备本机逻辑坐标；跨设备的用户布局由主机本地维护。屏幕更新造成焦点失效时应释放焦点。
- `0x10 ENTER`：长度 20；前缀后 `screen_id:u64, x:u16, y:u16, modifiers:u16, buttons:u8, reserved:u8=0`。坐标为该屏幕归一化 0…65535；modifiers 是左右 Shift、Control、Alt、Meta 的 8 位掩码和 Caps Lock 的 bit 8，其余位为零；buttons 的 bit 0…4 分别为左、右、中、后退、前进，其余为零。进入前必须检查屏幕存在、权限、焦点所有权及按键状态。当前共享会话实现仅接受零 modifiers 和零 buttons：主机适配时必须在物理按键和鼠标键松开后进入，不能只把非零状态清零，否则会丢失按键归属；进入时 Caps Lock 锁存状态的同步、带按键拖拽跨越均尚待实现或验收。
- `0x11 ENTER_ACK`：长度 12；前缀后 `screen_id:u64`。只有目标屏幕和 epoch 均匹配待确认请求才可接受。
- `0x12 RELEASE`：长度 8；前缀后 `reason:u8, reserved:3 bytes=0`；reason 0=普通切换、1=停用、2=故障恢复。
- `0x13 RELEASE_ACK`：长度 4，且只对当前待释放 epoch 有效。
- `0x15 CLIPBOARD_READY`、`0x16 CLIPBOARD_PAUSE`：长度均为 4，使用当前 focus_epoch。双方本地剪贴板 actor 均准备完成并互相收到 READY 后，才允许读取、发送或应用剪贴板。PAUSE 立即禁用并擦除当前传输，对该焦点不可逆；重新启用须 RELEASE/ENTER 获得新 focus_epoch。此前已在途的旧 epoch 或暂停后同 epoch 剪贴板帧，只做有界结构校验并静默擦除丢弃，不能写入、取消新传输或导致焦点错误。焦点切换立即恢复本地输入，异步等待剪贴板 actor 撤销完成后才允许新焦点；等待必须有期限。
- `0x14 REQUEST_LEAVE`：长度 16；前缀后 `screen_id:u64, x:u16, y:u16`，表示受控端希望从屏幕边缘离开，由主机根据布局决定下一步。
- `0x1e HEARTBEAT`：长度 12；前缀后 `nonce:u64`，仅用于诊断，不是授权凭据。
- `0x1f BYE`：长度 8；前缀后 `reason:u8, reserved:3 bytes=0`；reason 0=普通退出、1=权限失效、2=协议错误。

## Input（frame kind 2）

必须处于匹配的已确认 focus_epoch。目标端不能仅凭输入帧中的修饰键掩码注入任意未配对输入；按下、重复、释放和断线释放要保持一致。

- `0x01 MOVE`：长度 16；前缀后 `screen_id:u64, x:u16, y:u16`，均为目标屏归一化坐标。只允许合并连续移动，任何非移动事件前应先发送待发移动。
- `0x02 BUTTON`：长度 20；前缀后 `screen_id:u64, x:u16, y:u16, button:u8, down:u8, buttons:u8, reserved:u8=0`。button 1…5 对应左、右、中、后退、前进；down 为 0/1，buttons 掩码须与此次变更后的状态一致。
- `0x03 WHEEL`：长度 12；前缀后 `horizontal:i32, vertical:i32`，每轴按常规离散滚轮一格为 120 的相对单位，范围 −120000…120000；零轴不发送对应滚动。各设备反向和速度在主机上分别设置，目标平台适配原生滚轮事件。
- `0x04 KEY`：长度 12；前缀后 `usage:u16, modifiers:u16, down:u8, repeat:u8, reserved:u16=0`。usage 使用 USB HID Keyboard/Keypad page 0x07 编码（不包含 page 本身），modifiers 同 ENTER；down/repeat 均为 0/1，release 时 repeat 必须为 0。系统特殊键、输入法、快捷键习惯转换和平台不支持的键必须按能力和映射处理，不把键码当作文本。

## Clipboard（frame kind 3/4）

只有双方协商对应能力、用户允许且目标焦点仍有效时才读取或发送；非活动目标不广播。一次连接最多一个进行中的接收传输。应用程序应在远端结果写入前再次核对目标和本地剪贴板版本；发生本地冲突以本地改动为先。平台层校验 UTF-8／图片、拒绝文件引用并限制解码尺寸；使用后台任务，不记录内容。

- kind 3 opcode `0x01 START`：长度 20；前缀后 `transfer_id:u64, format:u8, reserved:3 bytes=0, total:u32`。同连接内 ID 非零且严格递增；format 1=UTF-8 文本（最多 2 MiB，允许空文本）、2=单张 PNG（1…16 MiB）。声明超过上限即拒绝，不分配对应缓冲。
- kind 3 opcode `0x02 CANCEL`：长度 16；前缀后 `transfer_id:u64, reason:u8, reserved:3 bytes=0`。取消或焦点变化时擦除未完成的本地缓冲。
- kind 3 opcode `0x03 INITIAL_DONE`：长度 4，每个焦点仅由主机发送一次。双方 READY 后，主机先发送当前文本/PNG 的完整快照，或明确跳过不支持的内容，再将此标记排入与 START/CHUNK 相同的 FIFO；不得用高优先级控制队列使标记越过分片。接收端以 ENTER 时采样的剪贴板版本保护初始快照，若本地已有新变化则保留新内容；收到标记后还须等待此前的本地验证/应用任务完成，才能向主机发送目标侧更新。暂停、释放或断线会撤销本阶段。
- kind 4 opcode `0x01 CHUNK`：长度 17…65536；前缀后 `transfer_id:u64, offset:u32, bytes:1…65520`。offset 必须等于已接收总字节数，ID 和焦点匹配，累计不得超过声明长度；达到 total 即完成。空文本由 START 直接完成。不能凭 TLS 加密忽略内容校验；损坏、重复或乱序分块不得写入系统剪贴板。

目前共享核心只覆盖有界分帧、序号、优先队列、内存重组与部分焦点策略，尚无上述 payload codec、证书确认流程、真实系统粘贴板联通或网络应用接线。实现和测试需要覆盖不同平台、控制延迟、断线、恶意输入、会话撤销及真实设备验收。
